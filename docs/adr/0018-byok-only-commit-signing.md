# ADR-0018: Container workers sign with a provided key, never a minted one

- **Status:** Accepted
- **Date:** 2026-08-19
- Narrows ADR-0006's worker contract, which offered key autogeneration
  alongside bring-your-own-key.

## Context

A container worker that pushes commits may need them to show as **Verified** on
GitHub, and there is no GPG or password-manager agent inside the container. The
worker therefore signs with an SSH key, and the key had three sources: a mounted
key (`GIT_SIGNING_KEY_FILE`), an autogenerated one (`GIT_SIGNING_AUTOGEN=1`,
which minted an ed25519 key and registered it on the token's GitHub account,
idempotent by title), or off.

Autogen carried two costs. It required the worker's token to hold
`admin:ssh_signing_key` (write) — a token that also lives in a session running
with permissions skipped, so the blast radius of that token widened to "can
manage signing keys on the account". And because registration was idempotent
*by title*, two workers that did not share a key volume clobbered each other:
the second minted a fresh key and re-registered the shared title, leaving the
first worker signing with a key GitHub no longer recognized. Its commits then
showed **Unverified** — silently, and only on the account where verification was
the point.

## Decision

Support bring-your-own-key only. `GIT_SIGNING_KEY_FILE` points at a mounted
private key, staged to a 0600 path and used as-is; unset means signing is off.
Workers never mint, register, or delete keys, and the signing path makes no
GitHub API call, so no worker token needs `admin:ssh_signing_key`.

## Alternatives Considered

- **Keep autogen, fix the clobbering** (per-instance key titles, or require a
  shared key volume). Pros: preserves zero-setup signing for a single worker.
  Cons: per-instance titles leave orphaned keys accumulating on the account with
  no cleanup owner; requiring a shared volume is BYOK with extra steps and an
  API scope. The token scope stays either way, which is the larger objection.
- **Mint locally, never register** (sign with an unregistered key). Pros: no API
  scope, no clobbering. Cons: GitHub marks commits from an unregistered key
  Unverified, so it produces exactly the outcome the feature exists to avoid.
- **Drop signing from workers entirely.** Pros: the smallest surface; unsigned
  commits are honest about being machine-authored. Cons: some repos enforce
  signed commits, which would make those repos undispatchable. Rejected as too
  narrow, though it remains the effective default (signing is off unless a key
  is mounted).

## Consequences

- Worker tokens need no signing-key scope. A compromised worker cannot register
  a signing key on the account it can push to.
- Multi-worker fleets are safe by construction: every instance reads the same
  provisioned key, and reading never races.
- Zero-setup signing is gone. Anyone who wants Verified worker commits must
  provision a key out of band and mount it — a documented step in the README,
  and the same step a fleet already needed for correctness.
- `bin/signing-selftest.sh` is removed with the mode it verified.
